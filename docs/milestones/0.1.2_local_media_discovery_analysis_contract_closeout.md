
The discovery contract is intentionally narrow:

- approved root: `/mnt/nas/movies/DVD`;
- candidates: regular `.mkv` files only;
- recurse through movie subdirectories under the approved root;
- do not follow symlinks;
- ignore non-MKV files;
- exclude filenames containing the case-insensitive marker ` - DVD RVE `;

- return deterministic ordering by relative path.

The discovery service does not expose arbitrary server filesystem contents and does not allow arbitrary host traversal.

## ffprobe Contract

Implementation location:

```text
app/services/media_analysis.py
```

The ffprobe invocation uses safe structured subprocess arguments with `shell=False` semantics by default:

```python
subprocess.run([
   "ffprobe",
   "-v",
   "error",
   "-print_format",
   "json",
   "-show_format",
   "-show_streams",
   "-show_chapters",
   str(source_path),
], capture_output=True, text=True, timeout=30)
```

The parsed result includes:

- source identity (relative to the approved root);
- duration;
- container/format name;
- size when available;
- primary video codec, width, height, `pix_fmt`, SAR, DAR, field order, frame-rate values;
- audio stream summary;
- subtitle stream summary;
- chapter count derived from the `chapters` collection returned by ffprobe, not guessed or silently defaulted to zero when chapter data is present.

If ffprobe fails or the file is structurally unreadable, the analysis result is returned as `unsupported` rather than guessed.

## Geometry Evidence

The geometry rule follows the v1 deterministic square-pixel calculation adopted in 0.1.0:

```text
display_width = round(coded_width * sar_num / sar_den)
display_height = coded_height
prepared_width = nearest_even(display_width)
prepared_height = nearest_even(display_height)
```

Examples:

- 720x480 anamorphic widescreen (`SAR 853:720`) → `854x480` prepared geometry
- 720x480 4:3 (`SAR 8:9`) → `640x480` prepared geometry

The implementation uses SAR as the primary source for square-pixel preparation and compares the derived display ratio to DAR. If the ratio divergence exceeds approximately 2%, the geometry result is returned as `review_required` rather than silently accepted.

## idet Sampling Contract

The analysis contract implements three bounded sample positions at approximately:

```text
20% of duration
50% of duration
80% of duration
```

The command shape is:

```text
ffmpeg
-v info
-nostdin
-ss <sample-time>
-i <approved-source>
-map 0:v:0
-vf idet
-frames:v 1000
-an
-sn
-dn
-f null
-
```

Bounded timeout:

```text
90 seconds per sample
```

The parser reads the final `idet` summary block from FFmpeg stderr, not the earlier zero-value preamble. For classification it uses only the final `Multi frame detection` counts:

- TFF count
- BFF count
- Progressive count
- Undetermined count

It separately retains the final `Single frame detection` TFF/BFF/Progressive/Undetermined counts as diagnostic evidence only. Single-frame and multi-frame counts classify the same decoded frame population and are never added together. The parser also retains the independent `Repeated Fields` counts:

- Neither
- Top
- Bottom

The original implementation used `-v error`, which suppresses the FFmpeg `idet` summary entirely. That caused the sample to be marked `insufficient` even when the installed FFmpeg was reporting valid counts. The parser was also vulnerable to the early zero-valued preamble output; it now prefers the final summary block and uses the final multi-frame values consistently.

## Classification Contract

The implementation uses a conservative classifier.

For each usable sample, it computes:

```text
determined = TFF + BFF + Progressive
progressive_ratio = Progressive / determined
tff_ratio = TFF / determined
bff_ratio = BFF / determined
repeated_population = Repeated Neither + Repeated Top + Repeated Bottom
repeated_field_ratio = (Repeated Top + Repeated Bottom) / repeated_population
```

The repeated-field calculation uses only its own classification population and does not mix in the TFF/BFF/Progressive population. A zero denominator produces a ratio of `0.0`.

Exact v1 thresholds and rules:

- A sample is `insufficient` when its multi-frame `determined` count is less than 100.
- `telecine_suspected`: any usable sample has `repeated_field_ratio > 0.10`; this check precedes clear progressive/interlaced classification.
- `progressive`: every usable sample has `progressive_ratio >= 0.95`, with both `tff_ratio < 0.25` and `bff_ratio < 0.25`, and no repeated-field signal above the telecine threshold.
- `interlaced_tff`: every usable sample has `tff_ratio >= 0.90`, with both `progressive_ratio < 0.25` and `bff_ratio < 0.25`, and no repeated-field signal above the telecine threshold.
- `interlaced_bff`: every usable sample has `bff_ratio >= 0.90`, with both `progressive_ratio < 0.25` and `tff_ratio < 0.25`, and no repeated-field signal above the telecine threshold.
- `ambiguous`: usable distributed evidence does not meet a clear rule, geometry requires review, or metadata materially conflicts with an otherwise clear content classification.
- `unsupported`: no usable sample evidence is available or required media evidence cannot be obtained safely.

No unsupported or ambiguous case is silently converted into a transform decision.

## Metadata / Content Conflict Handling

The result model keeps the distinction between:

- metadata `field_order` and
- actual content evidence from `idet`.

If metadata and actual content evidence materially disagree, the content classification is preserved as evidence but the final classification is downgraded to `ambiguous` rather than guessing. In particular, an interlaced ffprobe field order (`tt`, `bb`, `tb`, or `bt`) conflicts with strong progressive content evidence.

This matches the project’s manual workflow rule that metadata alone is not proof of the correct deinterlace path.
