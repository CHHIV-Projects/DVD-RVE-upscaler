# 5. Critical Preparation Eligibility Gate

Read-only discovery is intentionally broader than transformation eligibility.

A file being visible on `/media` does **not** mean it is safe to prepare.

Implement a dedicated preparation-eligibility service/predicate.

---

## 5.1 Base eligibility

A preparation candidate must:

- resolve beneath `/mnt/nas/movies/DVD`;
- be a regular `.mkv` file;
- not be a symlink;
- pass the existing source-containment rules;
- exist;
- be readable;
- remain on the approved read-only source root.

Reuse the accepted 0.1.2 source-validation logic where practical.

Do not create a competing path-security implementation.

---

## 5.2 Already-enhanced / suspicious candidate protection

The current library contains a known literal filename:

```text
Schindler's List/Schindler's List - DVE RVE Medium 2x.mkv
```

0.1.2 intentionally left this visible for read-only discovery because the approved minimal discovery exclusion marker was specifically:

```text
 - DVD RVE 
```

That is acceptable for **read-only analysis**.

It is **not** acceptable for transformation eligibility.

For preparation, implement a small conservative safety predicate that rejects filenames strongly indicating that they are already enhanced or RVE-derived.

At minimum, reject case-insensitive enhancement/version markers equivalent to:

```text
RVE
Nomos
Medium 2x
```

when present as filename/version markers.

Do not build a generic filename classifier.

Document the exact implemented predicate.

The known literal file:

```text
Schindler's List - DVE RVE Medium 2x.mkv
```

must be:

```text
discoverable/readable if otherwise valid
but
NOT PREPARATION ELIGIBLE
```

with a friendly reason.

Do not rename, delete, or modify it.

# 9. FFmpeg Preparation Filters

---

## 9.1 Progressive preparation

For an approved `progressive` preparation decision, use the validated conceptual sequence:

```text
scale=<prepared_width>:<prepared_height>
setsar=1
setfield=prog
```

Conceptually:

```text
scale=W:H,setsar=1,setfield=prog
```

The goal is:

- square-pixel output;
- correct display geometry;
- explicit progressive output state.

---

## 9.2 TFF preparation

For:

```text
deinterlace_tff
```

use the approved `bwdif` family path with explicit TFF parity.

Conceptually:

```text
bwdif=mode=send_frame:parity=tff:deint=all,
scale=W:H,
setsar=1,
setfield=prog
```

Do not use `send_field` unless new evidence explicitly justifies changing the accepted frame-rate behavior.

---

## 9.3 BFF preparation

For:

```text
deinterlace_bff
```

use the same path with:

```text
parity=bff
```

Do not derive parity from metadata after the Product Owner has explicitly selected a different preparation decision.

The explicit selected decision controls the preparation plan.

This is more than a placeholder response, but it should remain narrowly scoped to the preparation contract.

---

## 18.1 Required PASS checks

At minimum validate:

### File

```text
exists
non-zero
ffprobe-readable
```

### Video

```text
codec = h264
expected prepared width
expected prepared height
SAR = 1:1
field_order = progressive
pixel format = yuv420p or approved equivalent
frame rate consistent with the preparation plan
```

### Duration

Use the accepted v1 tolerance:

```text
abs(candidate_duration - source_duration)
<=
max(0.5 seconds, 0.5% of source_duration)
```

### Audio

Confirm expected audio stream count remains present.

Because the policy is stream copy, compare useful metadata where practical:

```text
codec
channels
language
```

### Subtitles

Confirm expected subtitle stream count remains present.

Compare codec/language where available.

### Chapters

If the source contains chapters and preservation was requested:

```text
prepared chapter count must match source chapter count
```
