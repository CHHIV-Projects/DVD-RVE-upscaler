============================================================
A. ACTIVE WORKFLOW / START NEW MOVIE HARDENING
============================================================

Problem already observed in real use:

When one movie finishes and another movie begins, parts of the UI can retain status/banners from the previous workflow.

Examples previously observed:

- a newly selected movie can show an old "Enhancement Complete" state
- later-stage highlighting can remain visible while the new movie is still at Find/Analyze
- recovery-oriented controls can appear during an ordinary fresh workflow

Required behavior:

1. Add a clear normal-user action:
   
   Start New Movie

2. Starting a new movie must reset the ACTIVE operator workflow presentation so that:
   
   - prior movie stage banners do not remain
   - prior preparation state does not appear as current
   - prior RVE state does not appear as current
   - prior finalization/publication state does not appear as current
   - current-stage highlighting returns to the correct beginning state

3. Historical records must NOT be deleted.

4. Starting a new workflow must not destroy:
   
   - previous workflow history
   - existing completed preparation artifacts
   - existing enhancement artifacts
   - prior finalization/publication evidence

This is an active-workflow reset, not historical deletion.

5. Existing durable workflow identity semantics should remain intact.

If the current data model does not cleanly support an active/new workflow distinction, make the smallest safe change required. Do not redesign workflow persistence.

Confirmed publication automount defect
=======================================

Immediately before 0.1.7, a live publication-readiness defect was fully diagnosed.

Configured publication root:

  /mnt/nas/dvd-upscaled-publication

Expected backing filesystem:

  //192.168.1.171/Movies/DVD Upscaled
  FSTYPE=cifs
  RW
  dedicated account=dvd-rve-publisher

The path is configured using systemd x-systemd.automount.

Observed dormant state:

  findmnt -T /mnt/nas/dvd-upscaled-publication

returns only:

  systemd-1  autofs  rw,...

A harmless filesystem access activates the backing mount.

After activation:

  findmnt -T /mnt/nas/dvd-upscaled-publication/<existing-or-probed-path>

returns stacked rows:

  /mnt/nas/dvd-upscaled-publication systemd-1
      autofs rw,...

  /mnt/nas/dvd-upscaled-publication //192.168.1.171/Movies/DVD Upscaled
      cifs rw,...

systemd confirms the mount is healthy:

  What: //192.168.1.171/Movies/DVD Upscaled
  Active: active (mounted)

A controlled create/delete test in the dedicated publication root also passed.

Current defective code is in:

  app/services/finalization.py
  publication_root_status()

Its local findmnt helper currently returns the entire stdout:

  value = (process.stdout or "").strip()

Therefore stacked mount output becomes multiline values such as:

  TARGET:
    /mnt/nas/dvd-upscaled-publication
    /mnt/nas/dvd-upscaled-publication

  FSTYPE:
    autofs
    cifs

  SOURCE:
    systemd-1
    //192.168.1.171/Movies/DVD Upscaled

  OPTIONS:
    rw,...autofs...
    rw,...cifs...

This causes false publication failures such as:

  "Publication root is not a distinct narrow mount point."

and potentially:

  "Publication root is not a verified NAS filesystem."

Required correction
===================

1. Preserve all existing publication safety boundaries.

2. Publication readiness must safely trigger/respect the configured systemd
   automount before deciding whether the backing filesystem is valid.

3. Use a non-mutating/read-only probe to trigger automount activation.
   Do NOT create/delete a test file as part of normal readiness checking.

4. After activation, parse stacked findmnt results correctly and evaluate the
   actual backing filesystem row.

For the confirmed topology:

  autofs wrapper
      ↓
  CIFS backing filesystem

the effective publication evidence must come from the CIFS backing row.

5. Do NOT treat `autofs` alone as proof of a valid NAS filesystem.

If only autofs is visible and no approved backing NAS filesystem can be
verified, publication must remain blocked.

6. Preserve all existing requirements that the publication root be:

   - absolute
   - real directory / not symlink
   - distinct from broad Movies hierarchy
   - its own narrow mount point
   - approved NAS/network filesystem
   - matched to publication_mount_identity
   - writable
   - no-overwrite/collision safe

7. Do not solve this by accepting any row containing `rw` or `cifs`.

The selected effective row must represent the actual backing mount associated
with the configured publication root.

8. The publish endpoint already re-runs:

     self.publication_checker()

at publish time.

Preserve that behavior.

Do not cache or permanently trust an earlier readiness result.

9. A locally finalized PASS artifact must NOT need to be re-finalized merely
because the publication automount was dormant when finalization completed.

10. Add focused regression tests covering at minimum:

   a. normal single-row CIFS publication mount => PASS

   b. dormant autofs where backing mount activation succeeds and exposes CIFS
      => PASS after activation

   c. stacked autofs + approved CIFS RW => PASS

   d. stacked autofs + CIFS RO => FAIL

   e. autofs with no valid backing NAS mount => FAIL

   f. backing mount with wrong publication identity => FAIL

   g. broad Movies mount / non-narrow destination => FAIL

   h. readiness activation performs no write

   i. publish re-evaluates readiness live rather than requiring re-finalization

Do not change host fstab, systemd mount configuration, NAS permissions, or
publication credentials.
