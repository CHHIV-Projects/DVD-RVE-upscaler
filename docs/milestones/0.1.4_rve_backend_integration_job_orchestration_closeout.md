## 8. Single-Active-Job Contract

Job start uses `BEGIN IMMEDIATE` and a partial unique SQLite index covering:

```text
running
cancel_requested
```

This makes the one-active-job claim race-safe for the single application instance. There is no pending queue. A conflicting start reports:

```text
Another RVE enhancement job is already running.
```

## 9. RVE Process Launch Contract

The backend is launched asynchronously with:

```text
structured argument list
shell=False
start_new_session=True
controlled RVE working directory
stdout/stderr combined into the job-owned log
```

No GUI executable, arbitrary browser arguments, arbitrary environment injection, overwrite flag, CPU fallback, or alternate model/backend is used.

The start response waits only until process ownership is established, not for enhancement completion.

## 10. Process Ownership and Cancellation

The current manager retains the live process handle and verified PGID. Persisted PID/PGID values alone never authorize a signal.

Cancellation:

```text
running
→ cancel_requested
→ SIGTERM to the verified owned process group
→ 10-second grace period
→ SIGKILL to that same group only if still alive
→ cancelled
```

No broad `pkill`, `killall`, or process-name signal exists.

Cancellation retains input, partial evidence, job records, and logs. It never publishes output or marks the job completed.

## 11. Shutdown and Restart Reconciliation

FastAPI lifespan shutdown marks an actively owned job `interrupted`, sends SIGTERM only to its owned group, waits within the same bounded grace period, and escalates only that group if required.

Startup changes stale durable `running` or `cancel_requested` rows to `interrupted` with:

```text
Application restarted while job was active; automatic process reattachment is not supported in v1.
```

No stale PID kill, automatic resume, rerun, or retry occurs.

## 12. Progress and Logging Contract

Stable backend frame progress is parsed and persisted. Percentage is calculated from backend-reported current frame and ffprobe-derived expected input frame count. No elapsed-time estimate is invented.

If parsing is unavailable or malformed:

```text
progress_percent = null
```

and state/latest safe message remain available.

Each local job log records creation, resolved profile, exact structured command, backend stdout/stderr, progress, exit, cancellation, and validation evidence. Raw filesystem log access is not exposed.

## 13. Completion and Post-RVE Validation Contract

Exit code `0` alone is insufficient.

Completion additionally requires:

- output exists and is non-zero;
- ffprobe-readable video exists;
- width and height are exactly 2x the prepared input;
- frame rate is within 0.1%;
- duration is within `max(0.5 seconds, 0.5%)`.

Only then is the partial output promoted and the job marked `completed`. Missing or invalid output becomes `failed`.

Audio/subtitle evidence is reported factually but is not a completion requirement for this bounded milestone validator.
