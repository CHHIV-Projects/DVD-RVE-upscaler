## 6. Media Analysis Recommendation

The required v1 logic should be a conservative content analyzer using metadata plus actual-content sampling. The key project rule remains valid: do not decide deinterlacing from `ffprobe field_order` alone.

Recommended v1 classification model:

- `progressive`
- `interlaced_tff`
- `interlaced_bff`
- `telecine_suspected`
- `ambiguous`
- `unsupported`

Recommended strategy:

- Read `ffprobe` metadata for resolution, SAR/DAR, fps, codec, and stream layout.
- Sample several distributed points across the main feature rather than a single frame or a single location.
- Use `idet` over a representative frame window to summarize repeated fields and progressive detection.
- Flag disagreement between metadata and actual frame evidence as a reason to stop for review.
- Treat telecine and cadence-sensitive content as `telecine_suspected` or `ambiguous`, not as a normal interlaced case.
- Require explicit Product Owner review for `ambiguous` material before any destructive preparation path is started.

This is consistent with the project’s explicit safety rule that ambiguous content must not silently receive a destructive conversion.

## 7. Geometry / Preparation Recommendation

The project’s validated geometry logic remains sound, and for v1 it should be implemented as a deterministic policy rather than a conceptual guideline.

Recommended v1 square-pixel policy:

1. Read the source coded width and height from `ffprobe`.
2. Read the source SAR (`sar_num`, `sar_den`) and define:
   - `display_width = round(coded_width * sar_num / sar_den)`
   - `display_height = coded_height`
3. Round to an even integer:
   - `prepared_width = nearest_even(display_width)`
   - `prepared_height = nearest_even(display_height)`
4. For a progressive preparation file, set square-pixel output to `setsar=1` and use the resulting `prepared_width`/`prepared_height` pair.
5. If the source SAR is missing, invalid, or conflicts materially with the DAR / expected DVD shape, classify the media as `ambiguous` or `unsupported` instead of guessing.

Common DVD cases:

- 720x480 anamorphic widescreen:
  - For NTSC DVD anamorphic widescreen, SAR is typically approximately `853:720` (or equivalent near-1.18 ratio).
  - `display_width = round(720 * 853 / 720) = 853`
  - `prepared_width = nearest_even(853) = 854`
  - Result: approximately `854x480` square-pixel progressive output.
  - This matches the project’s validated baseline.
- 720x480 4:3 DVD:
  - For a 4:3 NTSC DVD, the SAR is typically near `8:9` (display width about `640` when `720 * 8 / 9 = 640`).
  - `display_width = round(720 * 8 / 9) = 640`
  - `prepared_width = nearest_even(640) = 640`
  - Result: `640x480` square-pixel progressive output.

SAR / DAR handling:

- Use SAR as the primary source of square-pixel conversion.
- Use DAR as a cross-check, not a blind override.
- If `SAR` and `DAR` disagree beyond a narrow tolerance (v1: greater than about 2% difference for a DVD already identified as a standard DVD ratio), mark the content `ambiguous` and require review rather than auto-normalizing.
- This prevents false certainty when metadata is inconsistent with actual content.

Common DVD material patterns:

- `16:9` DVD content should normalize toward a square-pixel width around `854` for 720x480 NTSC material.
- `4:3` DVD content should normalize toward `640x480` (or the nearest equivalent even dimension) for the same coded source.
- The app should never silently apply a hard-coded 854x480 width to every DVD without deriving it from the observed SAR and coded geometry.

Recommended preparation pipeline conceptually:

- progressive source:
  - normalize geometry / SAR
  - ensure progressive state
  - NVENC preparation encode
- interlaced source:
  - deinterlace via approved `bwdif`-family logic
  - normalize geometry / SAR
  - NVENC preparation encode

This matches the project intent and the current tool availability.

## 10. Process Supervision and Cancellation Recommendation

The future application should treat FFmpeg and RVE jobs as per-job processes with explicit ownership. The direct Python backend supports the right model for this.

Recommended pattern:

- Spawn each job as a tracked child process and keep its PID in durable job state.
- Use a dedicated process group or explicit subprocess tree to avoid broad `pkill` behavior.
- Keep stdout/stderr logs in a per-job log file.
- Update job progress from the process output and/or structured status messages.
- Cancel only the job-owned process tree.
- On browser refresh or service restart, do not assume the old UI is still controlling the process.

The project rule remains correct: termination logic must never be broad or shared-host destructive. A job is only allowed to stop the processes it owns.

## 14. Output Validation Contract

Recommended v1 validation contract:

- `PASS`: output file exists, is non-zero, probes successfully, has expected geometry/codec/stream counts, and passes duration checks within an explicit tolerance.
- `BLOCKING WARNING / REVIEW REQUIRED`: output may be useable but has a material mismatch, ambiguous signal, or incomplete validation that must stop publication until Product Owner review.
- `NON-BLOCKING WARNING`: metadata-only or cosmetic issues such as missing optional language tags or a non-critical metadata omission, provided the essential stream and duration checks still pass.
- `FAIL`: output is missing, invalid, corrupted, wrong codec/geometry, wrong duration beyond tolerance, or broken stream structure.

Recommended v1 duration tolerance:

- Use `abs(candidate_duration - source_duration) <= max(0.5s, 0.5% * source_duration)` as the normal pass condition.
- This is sufficiently strict to catch significant duration drift while allowing normal encoder/container timestamp differences and small muxing variance.
- For a 90-minute movie, the tolerance is about `max(0.5s, 2.7s) = 2.7s`.
- For a 2-hour movie, the tolerance is about `max(0.5s, 3.6s) = 3.6s`.

Blocking validation outcomes:

- a missing/zero-length file
- `ffprobe` failure
- codec mismatch
- major resolution mismatch
- wrong SAR/DAR or square-pixel conversion beyond allowed tolerance
- wrong progressive/interlaced state for the selected pipeline
- audio/subtitle stream loss or major count mismatch
- chapter preservation failure when expected
- duration difference greater than the tolerance
- any validation result that could lead to a silent publish of a bad output

Non-blocking validation outcomes:

- optional language tag missing
- minor subtitle metadata inconsistency that does not affect output integrity
- a metadata-only cosmetic mismatch that does not alter media validity

The future app must not publish a `FAIL` result. `BLOCKING WARNING / REVIEW REQUIRED` outcomes should also stop publication until explicit review. `NON-BLOCKING WARNING` may remain visible but should not prevent publication if all blocking checks pass.

Checks should include at minimum:

- file exists and non-zero
- `ffprobe` can read the output
- expected codec / resolution / SAR / frame rate
- duration within the tolerance defined above
- audio stream metadata and count
- subtitle stream metadata and count
- chapters preserved where expected
- progressive/interlaced state consistent with the selected pipeline
